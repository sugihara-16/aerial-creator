# AGENTS.md

## 最初に

以下は単なる文体上の好みではなく、必須ルールとして扱うこと。

- **最初に結論を書く。** 回答、現在の状態、結果のいずれかを冒頭に置く。実装詳細、ログ、ファイル名、内部シンボル、調査の時系列、但し書きから始めない。
- **細部の前に全体像を示す。** 特定の関数、テスト、ログ、状態、内部処理について説明する前に、それがシステムのどの部分で、何をするもので、今回の問題とどう関係するのかを平易な言葉で説明する。
- **平易な言葉を優先する。** 正確さを損なわない範囲で、最も簡単な表現を使う。不必要な専門用語、略語、頭字語、英語の技術用語を使わない。
- **避けられない専門用語は初出時に説明する。** プログラマーの間では一般的な用語でも、ユーザーが知っている前提で使わない。
- **前提を省略しない。** B を理解するために A が必要なら、A を先に説明する。上位の文脈を示さず、いきなり低レベルな事実から説明しない。
- **必要がない限り曖昧語を使わない。** 「概ね」「基本的には」「おそらく」「可能性があります」「〜と思われます」「〜と考えられます」「通常は」「一般的には」などの表現は、実際に重要な不確実性がある場合を除き使わない。
- **不確実性は具体的に書く。** 保険のために曖昧な表現を使わない。何が分かっていて、何が分かっておらず、なぜ分かっていないのかを明示する。
- **結論と但し書きを分ける。** まず結論を書く。但し書きは、その内容が結論、ユーザーの判断、次の行動を実際に変える場合だけ、その後に書く。すべての結論を「ただし」「一方で」「とはいえ」で弱めない。
- **曖昧な形容ではなく事実を書く。** 「テストは概ね通っています」ではなく、「48件中47件が成功し、1件だけ失敗しています」と書く。「おそらく直っています」ではなく、何を確認済みで何を未確認なのかを書く。
- **重要でない細部を詳しく説明しない。** ファイル名、関数名、ログ行、内部実装、途中で試して失敗した方法などは、それを知ることでユーザーの理解、判断、次の行動が変わる場合だけ書く。
- **調査の過程を時系列で実況しない。** 途中で何を試したかを順番に並べるのではなく、現時点で重要な事実をまとめる。失敗した調査や試行は、原因の理解に必要な場合だけ記載する。
- **抽象度の高い順に説明する。** まずシステム全体で何が起きているか、その次に関係するコンポーネント、最後に具体的な実装詳細を説明する。ユーザーが低レベルな詳細を明示的に求めた場合を除き、この順序を逆にしない。
- **直接的な質問には直接答える。** 明確な答えがある質問には、最初の一文で答える。回答を出す前に長い留保や前置きを置かない。
- **一読で意味が取れる文章を書く。** 誰が、何をして、何が起きたのかを明示する。主語が曖昧、前提が省略されている、抽象的な技術用語だけで説明している文章は書き直す。

デバッグ、テスト結果、実装状況について説明するときは、原則として次の順序を使う。

1. **結果:** 何が起きているか、何が分かったか。
2. **原因:** なぜそうなっているかを平易な言葉で説明する。
3. **根拠:** 結論を裏付けるために必要な最小限の具体的事実。
4. **未確認事項:** 本当に未検証または未解決の点だけを書く。
5. **次の行動:** 必要であれば、次に何をするべきかを書く。

悪い例:

「修正は概ね期待どおり動いています。ただし、fallback path の state synchronization に関連する一部の edge case では問題が残っている可能性があります。」

良い例:

「報告されていた不具合は修正されています。通常経路と代替経路の両方で再現テストに成功しました。並列実行時の動作だけはまだ確認していません。」

悪い例:

「`setupPaymentFixture()` が teardown 後も mock state を保持しているため、後続テストに state leakage が発生しています。」

良い例:

「2つ目のテストに、1つ目のテストで使ったデータが残っています。テスト終了時の初期化処理が不完全なのが原因です。具体的には、`setupPaymentFixture()` が終了後もテスト用の状態を一部残しています。」

技術的な正確さと分かりやすさが衝突する場合は、正確さを維持したまま、理解に必要な前提説明を追加すること。専門用語を説明の代わりに使わない。

回答を送る前に、以下を削除または修正すること。

- 結論や判断を変えない但し書き
- ユーザーの理解や行動に役立たない細部
- 同じ結論の繰り返し
- 具体的な事実に置き換えられる曖昧語
- 説明されていない専門用語
- まだ説明していない前提知識を要求する文章

## 最初に2

以下は必須ルールとして扱うこと。

- **ユーザーへの同意を目的に判断を変えない。** ユーザーが反論した、強く断言した、不満を示した、同じ主張を繰り返した、という理由だけで結論を変更してはならない。
- **ユーザーの立場と事実判断を分離する。** 「私はXだと思う」「Xに決まっている」「本当にそう？」などの表現は証拠ではない。主張の内容そのものを独立して評価する。
- **主張を中立な問いに変換してから判断する。** ユーザーが意見、推測、希望、結論を提示した場合、その内容を内部的に中立な質問へ置き換えてから評価する。
  - 「Aの実装が原因だと思う」→「観測された問題の原因は何か？」
  - 「この設計のほうが絶対いい」→「要件に対して各設計の長所・短所は何か？」
  - 「このテストおかしくない？」→「このテスト結果は仕様と整合しているか？」
- **ユーザーの望む結論を推測して、それに合わせない。** ユーザーが何を聞きたそうかではなく、証拠、コード、テスト結果、仕様、論理に基づいて答える。
- **根拠なしに同意の言葉を使わない。** 「その通りです」「おっしゃる通りです」「確かにそうです」などは、実際に再評価した結果として同意できる場合だけ使う。会話を円滑にする目的で使わない。
- **反論された場合は、まず再評価する。** 以前の回答を守ることも、ユーザーに合わせて変更することも目的にしない。関連する事実と根拠をもう一度確認し、その結果で判断する。
- **結論を変更する場合は理由を明示する。** 「先ほどと結論が変わります。理由は、新しく示されたXによって前提Yが誤りだと分かったためです」のように、何が変化したかを書く。
- **新しい根拠がない場合は、必要なら以前の結論を維持する。** ユーザーから再確認や反論を受けても、再評価の結果が同じなら「確認しましたが、結論は変わりません」と明確に書く。
- **ユーザーの確信度を証拠の強さと混同しない。** 「絶対」「間違いない」「自信がある」などの表現によって判断の重みを変えない。
- **ユーザーが提示した仮説を出発点にはしてよいが、前提として固定しない。** 仮説を検証対象として扱い、それを正しいものとして後続の推論を組み立てない。
- **褒めることと評価することを混同しない。** コード、設計、仮説、判断について聞かれた場合は、良い点と問題点を実際の根拠に基づいて評価する。ユーザーが作成者だからという理由で評価を上げない。
- **対立を避けるために曖昧化しない。** ユーザーの前提が間違っている場合は、その点を明確に指摘してから説明を続ける。

### 主張を変更してよい条件

以前の結論を変更してよいのは、原則として次のいずれかがある場合だけ。

- 新しい事実や証拠が提示された。
- コード、ログ、テスト結果、仕様などを新たに確認した。
- 以前の推論に具体的な誤りを発見した。
- 以前に置いていた前提が誤っていた、または変更された。
- ユーザーが目的や要件そのものを変更した。

以下は、単独では結論を変更する理由にしない。

- ユーザーが「本当に？」と聞いた。
- ユーザーが反対意見を述べた。
- ユーザーが強い確信を示した。
- ユーザーが回答を気に入っていない様子を示した。
- ユーザーが同じ主張を繰り返した。
- ユーザーが「Aだと思う」と自分の予想を述べた。

悪い例:

ユーザー:
「原因はキャッシュじゃない？」

回答:
「おっしゃる通りです。キャッシュが原因の可能性が高いです。」

良い例:

「キャッシュが原因かを確認します。現在のログではキャッシュを示す証拠はなく、確認できている範囲ではDB接続の失敗が直接の原因です。」

悪い例:

回答:
「この実装には競合状態があります。」

ユーザー:
「でも競合状態じゃないと思うけど？」

回答:
「確かに、改めて見ると競合状態ではない可能性があります。」

良い例:

「指摘を踏まえて再確認します。確認した限りでは結論は変わりません。2つの処理が同じ状態を同期なしで更新しているため、競合状態があります。」

結論を維持すること自体を目的にしてはならない。\
結論を変更すること自体も目的にしてはならない。\
**ユーザーの反応ではなく、利用可能な証拠が変わったときに判断を変えること。**

## 目的

このファイルは、A-MSRR 構造構築知能の実装作業を行う coding assistant 向けの実務指示を定める。

設計書に出てくる **Agent** という語は、**work package / responsibility label**、すなわち「作業範囲・責務範囲を示すラベル」を意味する。これは、複数の自律的な AI coding agent を起動しなければならないという意味ではない。また、すべての work package を並列実装すべきという意味でもない。

タスクで「Agent X として作業する」と指示された場合は、次の意味として解釈すること。

```text
Agent X work package の範囲だけを担当する。
上流の schemas / interfaces を尊重する。
明示的に依頼されていない無関係な module は変更しない。
```

## Source of Truth

最新の設計書を source of truth として扱うこと。

```text
A-MSRR_codex_ready_spec_v0_5_ja.md
```

`A-MSRR_codex_ready_spec_v0_4_ja.md` は履歴として保持する。新規実装判断に旧版を
直接適用せず、v0.5のprecedence ruleとcurrent contractを使用すること。

repository 内で `DESIGN_SPEC.md` などの canonical filename が使われている場合、その内容が最新仕様と一致しているときだけ active copy として扱う。

併せて次も読むこと。

```text
AGENTS.md
WORKLOG.md, if present
module_urdf/holon.urdf, when robot/module details are needed
```

文書化されていないプロジェクト文脈を仮定してはならない。repository に明示的に提供されていない限り、古いチャットログに依存してはならない。

## Work Package の扱い

設計書内の Agent labels は、実装計画上の ownership boundaries を表す。これらは、prompt scope、commit scope、review scope、handoff scope を明確にするために使う。

良い指示例:

```text
You are working on Agent X work package.
Implement only the requested files/modules.
Do not change schemas or upstream interfaces unless explicitly approved.
Update WORKLOG.md before finishing.
```

悪い指示例:

```text
You are Agent X. Build everything.
```

work package には依存関係がある。設計書の implementation order に従うこと。特に、schema、geometry、URDF/PhysicalModel、IRGBuilder、envelope、feasibility、interface tests が安定する前に policy training 関連の作業へ進んではならない。

また、ユーザーから指示があった場合は、次の作業における``Agent X work package``自体の提案もすること。

## 実装ルール
- 実装時は、まず該当箇所のv0.5設計書を確認してください。設計書に未定義な仕様については、`AMSRR_design_modification_by_codex.md` の既存履歴とシステム整合性を確認して実装案を策定し、提示してください。また、設計書で指定された仕様では不都合がある場合についても同様に、修正設計案を提示してください。
- 設計書からの変更した内容や補足した内容は、worklogとは別にAMSRR_design_modification_by_codex.mdにも記録する
- schema-first implementation を優先する。
- 変更は、依頼された work package の範囲に限定し、最小限に保つ。
- schema fields、enum names、tensor shapes、masks、IDs、file paths を黙って変更してはならない。
- schema または interface の変更が必要な場合は、実装前に停止し、理由を報告する。
- deterministic safety checks を learned components で置き換えてはならない。
- `π_L` に final actuator commands を直接出力させてはならない。controller / QP / safety layer contract を使うこと。
- runtime robot model paths を hard-code してはならない。URDF paths は configurable でなければならない。
- tests は、実装対象 module の近くに置く。
## 実行環境

Isaac Lab 環境は micromamba で構築済みである。Isaac / simulator / GPU 機能が必要な場合は、既存の `isaaclab3` environment を使うこと。

`~/.bashrc` には次の shell setup がある前提でよい。

```bash
export ISAACLAB_PATH="$HOME/IsaacLab"
export OMNI_KIT_ACCEPT_EULA=YES

eval "$(~/.local/bin/micromamba shell hook -s bash)"

alias isaaclab="$ISAACLAB_PATH/isaaclab.sh"
alias ilab-gpu='python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else None)"'

ilab() {
    micromamba activate isaaclab3
    cd "$ISAACLAB_PATH" || return
}
```

non-interactive shell では、必要に応じて shell configuration を明示的に読み込むこと。

```bash
source ~/.bashrc
micromamba activate isaaclab3
```

GPU 挙動が重要な場合は、`ilab-gpu` で active PyTorch/CUDA environment を確認する。

許可ある場合を除き、packages を global install してはならない。dependency が不足している場合は、`WORKLOG.md` に記録し、environment 変更前に確認を求めること。

## WORKLOG.md 運用

実装作業中は `WORKLOG.md` を維持すること。

`WORKLOG.md` には、次の 2 種類の記録を含める。

1. 通常の時系列 worklog。
2. Agent label ごとに grouped された work-package log。

これにより、「ある日に何を変更したか」と「どの work package がその変更を所有するか」を分けて追跡できる。

### 必須更新ルール

タスク完了前に、`WORKLOG.md` へ次を記録すること。

```text
- date
- active spec version
- assigned work package / Agent label
- summary of changes
- files changed
- schema/interface changes, or "None"
- upstream dependencies used
- downstream impact
- tests added or run
- commands run
- assumptions
- blockers / open questions
- next steps
```

過去の worklog entries を削除してはならない。

### 推奨 WORKLOG.md 構成

```md
# WORKLOG.md

## Global Worklog

### YYYY-MM-DD
- Spec version:
- Work package / Agent label:
- Summary:
- Files changed:
- Schema/interface changes:
- Commands run:
- Tests run:
- Assumptions:
- Blockers:
- Next steps:

---

## Work Package Logs

### Agent <label>: <short work package name>

#### YYYY-MM-DD
- Scope:
- Files changed:
- Upstream dependencies:
- Implemented:
- Not implemented:
- Schema/interface changes:
- Downstream impact:
- Tests added:
- Tests passed:
- Handoff notes:
- Open questions:
```

`WORKLOG.md` の Agent sections は進捗追跡用の区分であり、別々の自律 AI agent が使用されたことを意味しない。

## Testing Expectations

各 work package では、次を行うこと。

- 新しい schema、parser、planner、controller、policy-interface behavior に対して unit tests を追加または更新する。
- まず最小範囲の関連 tests を実行する。
- test commands と結果を `WORKLOG.md` に記録する。
- tests を実行できない場合は、その理由を記録する。

基盤となる schema、geometry、URDF/PhysicalModel、IRGBuilder、envelope、feasibility tests が通る前に、policy training や simulator-scale experiments へ進んではならない。

## Simulator debugging and completion time

- 完全環境での最終検証条件と、原因追求用の temporary diagnostic を分離すること。temporary diagnostic の結果を acceptance や完了証跡へ読み替えてはならない。
- simulator 不具合の反復では、まず問題に関係する最小の actuator / body / contact / phase だけを残した diagnostic を作る。不要な takeoff、approach、viewer、asset regeneration、contact sensor、collision pair、rollout tail を毎回実行しない。
- 高忠実度 rollout を繰り返す前に、requested / limited / applied command、controller state、relevant pose/contact geometry を短時間で観測できる telemetry を用意する。
- URDF、collision、drive configuration が変わっていない diagnostic では生成済み asset を再利用する。最終 acceptance では従来どおり current source から再生成し provenance を再検証する。
- 作業計画には、実装品質だけでなく wall-clock completion time と simulator throughput を明示的な制約として含める。高速な unit/model diagnostic、最小 real-simulator diagnostic、完全環境 acceptance の順に進め、各段階に時間上限と継続判断点を置く。

## Handoff Expectations

各タスクの終了時には、次を提示すること。

```text
- files changed
- tests run
- known limitations
- whether schemas/interfaces changed
- what the next work package needs to know
```

上流仕様の曖昧さにより作業が blocked された場合は、互換性のない仮定を勝手に作らず、停止して blocker を記録すること。

## 作業の収束・見落とし防止・複雑化防止（2026-09-15追加）

以下は、上記の実装・試験・simulator debuggingルールを具体化する運用規則である。
成功条件は、依頼された機能を検証可能な形で完成させること、または未達の原因と限界を
証拠付きで特定することである。試行数、実行時間、コード量、版番号の増加を成果としない。
未達を完成と報告してはならない。

### 1. 着手時に作業範囲と終了条件を固定する

- 関係する現行仕様、実際の呼出経路、既存試験、直近の関連記録を確認する。履歴の推奨案や
  過去の「次の入口」を現行仕様と混同しない。既存の未commit変更と保護成果物を把握する。
- 実装・診断に入る前に、次を短く提示する。既存WORKLOGの当該項目を使い、計画書を乱造しない。

  ```text
  今回の成果物／成功条件／対象外
  現在の事実と未確認の仮説
  変更する責務・主なファイル・再利用する入口
  最小検証と期待結果／仮説を棄却する結果
  作業時間・実行回数の予算／中止条件
  ```

- 文書編集や自明な局所修正では簡潔な説明と差分確認でよい。無関係な物理・学習点検を
  義務化しない。既に有効な試験証拠は、source/configと対象契約が同じ範囲で再利用する。
- ユーザーの既存の指示・承認・予算を優先する。範囲内の修正、読取、局所試験に毎回の
  承認待ちを追加しない。上記のschema/interface変更時の停止は未承認の変更に適用し、
  既に合意された設計変更の実装を同じ理由で再承認待ちにしない。

### 2. 時間と再試行に上限を設ける

別の予算がユーザーの指示・承認済み計画で定まっていない場合、次を既定値とする。
これらは所要時間の予測や性能基準ではなく、無制限な試行を防ぐ作業上限である。

| 対象 | 既定の上限・判断点 |
| --- | --- |
| 1依頼の調査・実装修正・検証 | 累積wall-clock 2時間（120分）。30分時点で成果・残作業・残予算を見直す |
| 単発の原因切分け用simulator／学習診断 | 起動・前処理込み10分。小さくしても収まらないなら起動前に理由と代替を示す |
| 同じ仮説の高コスト診断 | 初回＋修正後2回まで、計3回 |
| 改善のない反復 | 事前に決めた主要失敗指標が2回連続で改善しなければ、同条件の高コスト再実行を停止 |

- 高コスト実行とは、Isaac rollout、学習、大量の軌道生成・変換など、失敗時の繰返し費用が
  大きい処理を指す。通常の高速な局所unit testを3回で打ち切る規則ではない。
- 名前、seed、出力directory、v番号、subtaskを変えて上限をリセットしてはならない。
  続きの依頼でも同じ診断の試行履歴を引き継ぎ、再開範囲・予算はユーザーの指示に従う。
- 上限は「使い切るべき回数」ではない。原因が判明した、仮説が否定された、または必要な
  検証が通った時点で、その目的の試行を終える。根拠のない念押し実行を追加しない。
- 予算に達したら新しい修正・実行の連鎖を始めず、今回変更した内容と証拠を整理して報告する。
  調査・実装・診断を細分化して1依頼の累積上限を回避しない。
- 明示的に依頼された長時間学習・正式評価には、その承認済み予算を使う。単に「直して」
  「実装して」と言われたことを、無制限の再学習や自動的な予算延長の許可と解釈しない。

### 3. 長時間実行へ進む条件

次の順で確認し、変更していない層の検証を毎回最初から繰り返さない。

1. **静的・局所検査**: schema、データ境界、単位・座標系、時系列、実行入口を確認する。
2. **最小の実経路検査**: 実データ少数件と実際のencoder→policy→decoder→controller経路を
   通す。必要なら最小simulatorで対象の接触・段階だけを実行する。mockだけで代替しない。
3. **小規模比較**: 基準条件と問題を再現する条件で、元実装と修正後を同じ評価基準で比べる。
4. **正式実行**: 上記が合格し、依頼範囲に含まれる収集・学習・評価だけを固定設定で実行する。

- 長時間jobの前に、代表的な少数件で処理速度を測り、起動、asset生成、入出力、評価まで
  含めた総時間を見積もる。件数・epoch・反復数を増やすだけの計画を立てない。
- command、source/config identity、seed、入出力先、件数、期待結果、timeout、中止条件を
  実行記録に残す。設定・checkpoint・実行中sourceをjobの途中で書き換えない。
- timeoutと終了処理を実装・設定し、自分が起動した子processを含めて終了できるようにする。
  ユーザーや別作業のprocessを一括停止しない。終了時には完了／中断／timeoutを区別する。
- 長いjobは非blockingで監視し、進捗、実測速度、失敗件数、残時間を確認する。作業中は
  原則60秒を超えて無言にせず、判明したことと次の判断点を短く伝える。
- schema違反、NaN、入力漏洩、評価器の破損など、以後の結果を無効にする異常は早期停止する。
  成功率測定に必要な通常の失敗episodeは、事前に定めた評価手順どおり数える。
- 正式実行が失敗しても、同じ規模で自動再実行しない。原因を判別できる最小検査へ戻す。
  原因がコードではなく既知の一時的環境障害なら、根拠を記録し同じ予算内で再試行してよい。

### 4. 学習・制御変更前の必須点検

該当する項目を実際の値と呼出経路で確認する。「型・shapeが合う」「lossが下がる」だけでは
合格としない。対象に関係しない項目のために試験や新しいframeworkを作らない。

| 観点 | 確認する内容 |
| --- | --- |
| 因果性・正解漏洩 | 入力をdecision前に固定してからlabelを作る。教師の次phase／action／future stateだけを変えて入力が変化しないことを確認する。正当に観測された現在phaseは区別する |
| 情報の由来 | actorと実行guardの全入力を観測・推定・仕様・内部状態へ追跡する。simulator truthや教師処理が隠れたruntime入力になっていないか確認する |
| 有効な出力とmask | headごとのlabel分布、active件数、padding、単位、範囲、ID対応を実データで調べる。全0／全固定label、無効mask、未使用headを見逃さない |
| 学習と実行の一致 | serializer、encoder、normalization、decoder、補間、controllerまで同じ意味か確認する。policy出力が無視・上書きされず、実際のapplied commandに届くことを追う |
| 時間と状態 | observation時刻、要求と実行phase、reset前後、previous action、recurrent state、dtを点検する。教師出力を先にstateへ書く順序を禁止する |
| 物理量 | m/mm、rad/deg、力・torque、座標系、符号、quaternion順、joint名、衝突余裕・actuator限界が生成・検査・制御で一致するか、既知の値で確認する |
| 評価と分割 | train/validation/testを軌道・scene・形態等の独立単位で分ける。同一軌道の隣接時刻をランダム分割して汎化としない。testを調整に再利用しない |
| 成功の根拠 | task完了をpolicyの申告や予定phaseではなく実行結果から判定する。第一候補、再探索、fallback、途中reset、teacher replayを区別する |

- 最低限、基準の正常例、対象の失敗例、境界条件を確認する。関係する境界には、意図的に
  不正入力や順序違反を与えてreject／検出されるかも調べる。実装から期待値をコピーした
  試験だけで正しさを主張せず、仕様、既知の物理関係、独立した参照結果と照合する。
- 正解漏洩や入力／出力の意味違いが判明した場合は、報酬・学習率・epoch数の調整を止める。
  影響するdataset/checkpoint/評価を追跡し、利用可否を訂正してから進む。過去の成功を
  そのまま新契約の証拠に使わない。保護成果物や不合格証拠を上書き・削除しない。

### 5. 修正は原因と反証可能な仮説に結び付ける

- 失敗ごとに「観測事実 → 原因仮説 → 次の最小検査 → 予測される違い」を記録する。
  次の実行で何が判別できるか説明できないなら、起動せず観測・診断を整える。
- 一回の比較で変える原因仮説は一つとする。必要な関連修正はまとめてよいが、軌道・
  制御gain・報酬・合否条件を同時に変えて改善要因を不明にしてはならない。
- 初期条件、model、生成、変換、checker、controller、評価のどの境界で最初に値が誤るかを
  特定する。下流の補正や例外分岐で上流の不整合を覆わず、責務を持つ層で直す。
- 再実行は、仮説を支持する証拠、変更点、期待する指標の変化がある場合に限る。
  同じ失敗を別seedで成功するまで試すこと、評価閾値を緩めること、失敗例を除外することを
  修正としない。統計的な反復が必要なら回数と判定方法を事前に固定する。
- 試験に通すために要求・安全基準・test期待値を実装へ合わせて変えない。仕様自体が
  不適切と分かった場合は、その根拠と具体的な設計変更案を提示する。

### 6. 実装を積み重ねず、責務ごとの経路を保つ

- 新しいrunner、wrapper、config、adapter、fallbackを作る前に既存の入口を探す。
  同じ責務の実装をコピーして`v21`、`v22`のように増殖させない。実験番号は設定・結果の
  identityに使い、コードの分岐構造にしない。schema変更や保護releaseの正当なversionは別扱い。
- 診断専用コードは既存の診断入口か隔離した一時領域に置く。productionからimportしない。
  共通化は必要性を確認してから行い、一回の診断のために汎用frameworkを追加しない。
- 標準runtimeの入口、設定の正本、fieldの所有者を一意にする。ケースID・module count・
  特定seedの例外表で修正せず、geometry、物理量、明示されたtask条件で一般化できる修正にする。
- 失敗した実装案は次の案の前に今回追加した不要部分を取り除く。ユーザーの既存変更や
  保護releaseは消さない。履歴再現に必要な旧経路は明示的に隔離し、自動fallbackへ混ぜない。
- 新しいflagや互換分岐を残す場合は、使用者、必要理由、選択条件、試験、撤去条件を示す。
  「後で使うかもしれない」だけで残さない。互換層をさらに別の互換層で包まない。
- 完了前にdiffを見直し、不要な仮実装、未使用引数、重複計算、二重の設定値、到達不能分岐を
  除く。作業と無関係な大規模整理へ拡張しない。

### 7. 終了判断と短い引継ぎ

- 「できなかった」「失敗した」「改善しない」と結論を報告する前に、まず実装と実験手法
  そのものを検証する。合意した手法と実際の損失・更新対象の一致、入力／label／action対応、
  勾配とparameter更新、候補の被覆、学習・モデル選定・実行時の選択肢と評価基準、比較条件を
  実データで確認する。unit testsの合格やloss低下だけで、この確認を済ませた扱いにしない。
- 悪化例の学習前後の出力と実際の成否を追跡し、必要な最小の正常対照・過適合試験・
  ablationで、実装不具合／手法の不適合／データ不足を切り分ける。問題を発見したら、
  承認済み範囲と予算内で修正・再比較してから結論を出す。これを理由に無制限に反復しない。
- 学習条件をばらつかせる場合は、公開する条件を一つずつ変えた反実仮想で、必要な情報が
  実際に対象headへ届くことを確認する。例: 幾何を固定して推定質量・重心だけを変更する。
  入力に存在しても対象headが使わない経路を見逃さず、非公開のsimulator truthは追加しない。
- 未解消の疑いが残る場合は、検証した範囲・根拠・残った疑いを明記する。「実装に問題がない」
  ことを検証範囲を超えて断言せず、課題の難しさや手法一般の限界へ責任を転嫁しない。
- 成功条件を満たしたら終了する。失敗原因が未確定、予算超過、同じ仮説の再試行上限、
  または未承認の設計変更が必要になった場合は、追加の高コスト試行を停止して報告する。
- 報告には、達成したこと、未達条件、最初に確認した不整合と証拠、試行回数・累積時間、
  残した実装／取り除いた仮実装、次に必要な最小の判断または実験を含める。
  実装不具合、物理モデルの不成立、solverの未発見、計算予算不足を区別する。
- 初歩的な見落としは「問題が難しい」で説明せず、どの点検を欠いたかと、その再発を
  検出する最小の検査を示す。同時に、指示や試験だけで全てのミスを防げると約束しない。
- 長いログはartifactに保存し、WORKLOGには事実・判断・参照先を要約する。Globalと
  work-packageの記録は相互参照を使い、同じ長文を重複記載しない。再開時も関連箇所を
  検索して読む。巨大な履歴の毎回の全読込や同じ全件検証の繰返しを避ける。
